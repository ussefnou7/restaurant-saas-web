## 1. R-1 — mechanism accepted; the dump is contradicted by a live screenshot

Stating plainly that no browser is installed, and relabeling §7 as **specification-computed**
rather than measured, is the right call. That is the honest fallback and it is accepted.

The arithmetic was spot-checked and is internally correct. Asset detail at 1920: 4 tracks ×
383.5px + 36px of gaps = 1570px inside a 1616px wrapper. That matches an independent
calculation. Asset detail at 2560: `auto-fit` creates 8 candidate tracks at the 260px minimum,
collapses 4 empty ones, sizes the remaining 4 to the 420px ceiling → 1716px, 540px parked.
Also correct.

**But one row of the dump is falsified by a screenshot taken after Phase 2 shipped.**

The dump asserts:

> Module Hub (/inventory) — 1920px — `.hub-nav-card-grid: minmax(280px, 360px)` —
> **4-up** (360px max, 1482px grid width, 134px parked end)

The rendered page shows **3-up**. Measured off the screenshot:

| Quantity | Value |
|---|---|
| Card width | ~353px |
| Column gap | ~21px |
| Card grid occupies | ~1102px |
| Row below it (`التقارير` + `الإعدادات`) spans | ~1470px |
| **Trailing empty space beside the grid** | **~368px** |

Under `repeat(auto-fit, minmax(280px, 360px))`, a fourth track requires `280 + 21 = 301px`.
**368 > 301.** `auto-fit` creates a track whenever the *minimum* fits — so a fourth column was
available and was not created.

Whatever the exact viewport, that inequality holds. The rule was therefore **not in effect at
render time**. Three candidates:

1. A more specific rule still resolving to `repeat(3, …)` overrides it.
2. The grid element itself carries a `max-width` around 1102px.
3. The browser was serving stale CSS (dev server not reloaded / hard-refresh not done).

**This is the point of the verification standard, demonstrated.** The dump is arithmetic
applied to the CSS Flash believes is deployed. It is rigorous and it is wrong, because the
premise — "this rule is what the browser resolves" — is exactly the thing arithmetic cannot
check. One screenshot falsified a row that no amount of spec-reading would have caught.

§7 stays labeled **specification-computed**, and this row is now known-bad. Do not re-derive
it; go measure it.

### Diagnostic to run first

```js
const g = document.querySelector('.hub-nav-card-grid');
const s = getComputedStyle(g);
console.log(g.className, '|', Math.round(g.getBoundingClientRect().width),
            '|', s.gridTemplateColumns, '|', s.justifyContent, '|', s.maxWidth);
console.log('parent:', g.parentElement.className,
            Math.round(g.parentElement.getBoundingClientRect().width));
```

- Grid width **equals** parent width → the rule is overridden; find the winning declaration.
- Grid width **less than** parent → the grid carries its own cap; remove it.
- `gridTemplateColumns` prints three tracks → confirm the deployed file actually contains
  `auto-fit`, then hard-refresh before concluding anything.

### A pattern worth naming

Two of the five items were closed against a selector different from the one raised, each
explained as an audit shorthand. Once is a naming slip. Twice means **the audit's §4 and §5
inventory tables cannot be trusted as a source of selector names** — and those tables are the

Not a criticism of the fixes, which look right. It is a warning about the map: when a later
phase says "covered per §5," that claim now needs its own verification. Re-verify §4 and §5
selector names against the actual stylesheets before Phase 3 leans on §5's table inventory.

## 6. Phase 3 — authorized, with one hard condition

The pre-flight restatement is correct and complete, in the right order: `min-width` floor
first, `.table-wrap` second, sticky column third. Authorized.

**The condition: Phase 3 cannot be verified by arithmetic at all.**

Phase 2 was at least partly computable — track sizing follows from the spec. Nothing in Phase 3
does:

- whether a scrollbar appears
- whether `overflow-x` engages against `table-layout: fixed`
- whether `position: sticky` holds against a scrolling ancestor
- whether the sticky cell's background actually occludes the content passing under it
- **whether RTL horizontal scrolling behaves** — the single most likely thing to break, and
  entirely a runtime engine behavior

None of these can be derived from reading CSS. A spec-computed Phase 3 report would be worth
nothing.

So Phase 3 ends in one of two states, and the choice is to be stated up front, not discovered
in the report:

- **Install a browser.** Chromium plus Playwright is usually available in this kind of
  environment; try it before assuming it is not. If it works, Phase 3 is verified properly and
  §7 can be re-measured for free while you are there.
- **Or hand the verification back.** Ship the implementation, mark it **unverified**, and
  deliver a numbered manual checklist — per table, per viewport, per direction, each item a
  single observable yes/no — for a human at a real browser to walk. That is a legitimate
  outcome. Silently computing it is not.

### The card/input amendment

The `360px` ceiling on `.hub-nav-card-grid` came from my A-3 and it was wrong. It transplanted
field-grid reasoning onto navigation cards. A text input past ~420px is functionally unusable;
a nav card is a click target with a title and one line of description and has no such failure
mode. Capping it only manufactures the dead space visible in the screenshot — and note that
even Flash's *own* prediction for that row conceded "134px parked end."

```css
.hub-nav-card-grid {
  grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
  justify-content: stretch;
}
```

With six hub cards: 3-up at ~976px, 4-up at ~1470px, 6-up on one row at ~2256px — filling the
row at every step, no trailing hole.

`.mini-stat-grid--compact` **keeps** its `minmax(200px, 300px)` ceiling. This is not
inconsistent: `auto-fit` collapses empty tracks, so a grid holding a small fixed number of
items and sized in `1fr` stretches those few items across the whole row. Four stat tiles at
`1fr` on a 2256px container are ~564px each. Six hub cards are not.

The governing rule, for the decision entry:

> A `px` ceiling belongs on a grid whose items fail when stretched — inputs (unusable past
> ~420px), or a small fixed set of tiles that would each absorb a quarter of a 2560px screen.
> A grid holding a variable number of cards that wrap to multiple rows takes `1fr` and fills
> the row. `auto-fit` + `1fr` stretches few items; `auto-fit` + a `px` ceiling parks the
> remainder at the inline end. Choose by item count, not by habit.

## 8. D98 — amended

D98 is otherwise accepted as drafted. Append this clause before the verification-standard
paragraph:

```markdown
**Ceilings belong on grids whose items fail when stretched.** Field grids carry a `px` ceiling
because a text input past ~420px is unusable. Grids of navigation cards or tiles that wrap
across multiple rows use `repeat(auto-fit, minmax(<floor>, 1fr))` and fill the row — a capped
card grid only manufactures dead space at the inline end. The exception is a grid holding a
small fixed number of tiles: `auto-fit` collapses empty tracks, so four stat tiles sized in
`1fr` stretch to ~564px each on a 2560px viewport. Those keep a ceiling
(`.mini-stat-grid--compact`, `minmax(200px, 300px)`). Choose by item count and failure mode,
not by copying the neighboring rule.
```
